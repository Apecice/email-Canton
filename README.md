# Canton 邮件到达 / 接收诊断工具

针对 `xxx@cantonservices.com.hk` 这类香港邮箱，在**中国大陆**用 Foxmail（及手机）
**经常收不到邮件、要重启客户端才收得到**，而**香港同事却正常**的问题，做证据采集。

> **隐私说明：本工具只采集元数据（邮件到达时间、Message-ID、大小、连接状态），
> 绝不读取、不下载、不保存邮件正文。** 发件人/收件人/主题默认做不可逆哈希处理，
> 生成的报告可以安全地发给邮件服务商或 IT。`config.ini` 和 `logs/`、`reports/`
> 都已被 `.gitignore` 忽略，不会上传到仓库。

---

## 一、先看结论（很可能的原因）

把你的现象排列一下：

| 现象 | 说明的事 |
|------|----------|
| 香港同事能正常收到**同一封**邮件 | 邮件**确实已经到达** `cantonservices.com.hk` 服务器，服务器收信没问题 |
| 你在大陆，Windows + 手机都收不到 | 不是 Foxmail 单个软件的 bug，是**网络路径**问题 |
| **重启客户端**就能把邮件收下来 | 典型的**长连接被中途静默掐断**：客户端以为还连着，新邮件通知永远不来；一重启重新握手，积压的邮件一次性全下来 |
| 供应商/美国的邮件更明显 | 这些邮件常在中国夜里到达，那时连接已挂很久、最容易被回收，并非邮件本身被针对 |

**初步判断：问题大概率出在"大陆 ↔ 香港的跨境连接稳定性"**（被防火墙 / NAT / QoS
在你不知情时掐断长连接），而**不是邮件服务器丢信**，也基本不是 Foxmail 本身。

这个工具就是用数据**把这个判断坐实**，让服务商/IT 没法甩锅。

## 二、你要采集的"证据"

1. **邮件到服务器的时间 vs 你客户端看到它的时间**
   每封新邮件记录两个时间：服务器侧 `INTERNALDATE`（服务器几点收到）和本工具在
   一条独立连接上**几点才发现它**。两者的差 `server_to_client_delay_sec` 就是延迟铁证。
2. **你那条长连接到底何时断、断了多久没人告诉你**
   IDLE 模式会长期挂着连接，并定期发 `NOOP` 探活。一旦出现 `noop_fail` / `drop`，
   就是"连接静默死亡"的凶器——这正好解释了"为什么重启就好"。
3. **网络层延迟与丢包**（`net_probe.py`）：到服务器 993/587/465 端口的 TCP/TLS
   连接耗时和失败率。
4. **两个观测点对比**（强烈建议）：
   - 出问题的**大陆 Windows** 上跑一份（`vantage = mainland-win`）
   - 一个**对照点**——香港同事的电脑，或一台香港/海外云主机（`vantage = hk-control`）
   两边数据一对比：若香港几乎零延迟、无断连，大陆延迟大/频繁断连，结论无可辩驳。

## 三、在 Windows 上怎么用（最省事的方式）

### 1. 装 Python
到 https://www.python.org 下载安装 Python 3.10+，安装时**勾选 "Add Python to PATH"**。

### 2. 填配置
把 `config.example.ini` 复制一份改名为 `config.ini`，按里面的中文注释填好：
邮箱服务器地址、端口、账号、密码（或授权码）。
> 不确定 IMAP 服务器地址，可在 Foxmail 的"账号设置 → 服务器"里看，通常是
> `imap.cantonservices.com.hk` 或类似，端口 `993`（SSL）。

### 3.（可选，推荐）装 IDLE 模式依赖
打开"命令提示符"，进入本目录后执行：
```
pip install -r requirements.txt
```
装了就能用 `idle` 模式（最能抓静默断连）；不装也行，会自动退回 `poll` 轮询模式。

### 4. 开始采集
- 双击 **`run_monitor.bat`** —— 启动邮件到达/连接监控
- 双击 **`run_netprobe.bat`** —— 启动网络探测（可与上面同时开着）

让它们**持续运行几天**（尤其覆盖你平时漏收邮件的时段，比如夜里到第二天早上）。
按 `Ctrl + C` 可停止。

### 5. 出报告
双击 **`make_report.bat`** —— 在 `reports/` 下生成一份纯统计、可外发的报告。

---

## 四、不用 .bat、直接命令行（Mac/Linux 同理）

```bash
pip install -r requirements.txt          # 可选，IDLE 模式才需要
cp config.example.ini config.ini         # 然后编辑 config.ini
python src/imap_monitor.py               # 监控邮件到达 + 连接健康
python src/net_probe.py --interval 60    # 另开一个窗口，网络探测
python src/report.py                      # 采集一段时间后出报告
```
强制指定模式：`python src/imap_monitor.py --mode poll`（或 `--mode idle`）。

## 五、生成的文件

| 文件（在 `logs/`） | 内容 |
|--------------------|------|
| `messages_<观测点>_<日期>.csv` | 每封新邮件：到达服务器时间、被客户端发现时间、延迟秒数、大小、（哈希后的）发件人/主题 |
| `connection_<观测点>_<日期>.csv` | 连接生命周期：connect / login / idle / **drop / noop_fail** / reconnect |
| `netprobe_<观测点>_<日期>.csv` | 每次到邮件端口的 TCP/TLS 连接耗时与成败 |

`reports/report_*.txt` 是上面三者的汇总，**只含统计、不含任何邮件内容**。

## 六、报告怎么读 / 发给服务商时怎么说

- **若 `INTERNALDATE` 远早于 `detected_at`**（延迟几分钟到几十分钟甚至几小时）：
  邮件早就到香港服务器了，是你的客户端拉不下来 → **问题在跨境连接，不在服务器投递**。
- **出现 `noop_fail` / `drop`**：你的长连接在悄悄死掉 → 这就是"为什么一重启就好"。
- **两个观测点对比**：香港≈0 延迟无断连、大陆延迟大且频繁断连 → **跨境链路是元凶**。

> 可以这样对服务商/IT 说：「同一封邮件，香港同事 X 点就收到了（服务器 `INTERNALDATE`
> 为 X 点），但我在大陆的客户端直到 Y 点重启后才拉到，期间监控记录到 IMAP 长连接
> 多次 `noop_fail`/`drop`。请协助排查从大陆到 `cantonservices.com.hk` 的 IMAP(993)
> 跨境连接为何被中断，并建议是否可启用更短的 IDLE 刷新、长连接保活，或提供更稳定的
> 接入点。」

## 七、能顺带缓解的几招（在等服务商处理时）

- 把 Foxmail 的**收件检查间隔改短**（如每 1–3 分钟），降低"漏掉新邮件通知"的影响。
- 优先用 **IMAP + SSL/TLS(993)**；如本来用 POP3，IMAP 一般更稳。
- 在路由器/防火墙上，尽量**延长到该服务器的 TCP 连接空闲超时**（NAT 老化时间）。
- 若公司有合规的稳定跨境网络/专线，让邮件客户端走它，往往能立刻改善。

> 这些只是缓解，**根因仍需服务商配合**——本工具的报告就是推动他们排查的依据。

## 八、安全性与测试

**数据安全**：本工具**绝不下载邮件正文**（只用 `BODY.PEEK[HEADER.FIELDS ...]` 取少量
头字段，连"已读"标记都不动），**绝不把密码写进日志**，发件人/收件人/主题默认哈希存储。
这些都有自动化测试持续守护（见 `tests/test_privacy.py`）。

**自动化测试**：纯标准库 `unittest`，**不联网、不需要真实邮箱**（用伪造 IMAP 客户端驱动）。

```
python -m unittest discover -s tests -p "test_*.py" -v
```
或在 Windows 上双击 `run_tests.bat`。覆盖：隐私不变量、配置校验、登录失败/文件夹错误
不再无限重连、暂时性网络错误重试、跨时区时间解析、IMAP 区间查询怪癖、优雅停止、
网络探测的 TCP/TLS 区分等。

各项缺陷的**根因分析与今后如何避免**见 [`docs/缺陷分析与防范.md`](docs/缺陷分析与防范.md)。
